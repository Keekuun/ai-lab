# LLM 工程基础：训练、推理与模型适配

> 本篇补齐 Agent 开发之前容易被跳过的一层：模型从哪里来、为什么会产生这些能力，以及部署和适配时真正需要关心什么。
>
> **边界：** 这里只讲训练 / 推理 / 微调决策。Schema 与 Tool 设计见 [09](./09-tools-system-design.md)，Parser API 见 [LC10](./langchain/10-output-parsers.md)。
>
> **配套实验：** [01 结构化输出](./examples.md#01-结构化输出) — 非法 JSON 拒绝并重试，不把脏数据交给业务。

## 学完要能回答什么

- 预训练、SFT、RLHF、DPO 分别解决什么问题？
- 为什么上下文变长会增加成本和延迟？
- KV Cache、Batching、量化分别优化什么？
- 什么时候应该换模型、改 Prompt、做 RAG，什么时候才值得微调？

## 一条完整链路

```text
数据清洗 → Tokenizer → 预训练 → SFT → 偏好对齐 → 推理服务 → 应用层
```

不要把“模型能力”和“应用效果”混为一谈。应用质量通常由模型、上下文、工具、数据和评测共同决定。

## Tokenizer 与上下文

模型看到的不是字符，而是 token。token 数量决定上下文占用、输入费用和部分延迟。

工程上至少要关注：

- 中文、代码、URL、表格的切分效率不同。
- `max_tokens` 是输出上限，不等于完整上下文容量。
- 历史消息、工具 Schema、检索片段都会占用上下文。
- 截断应按消息重要性、文档相关性和任务状态处理，不能简单取最后 N 条。

## 训练阶段的分工

| 阶段 | 目标 | 常见数据 | 应用开发者的判断 |
|------|------|----------|------------------|
| 预训练 | 学习语言和世界知识 | 大规模文本 | 通常不自己做 |
| SFT | 学习任务格式和行为 | 指令-回答 | 需要稳定风格或格式时考虑 |
| RLHF | 对齐人类偏好 | 排序和反馈 | 了解原理即可 |
| DPO | 直接使用偏好对 | chosen/rejected | 小规模定制时更易落地 |
| RAG | 注入外部、可更新知识 | 文档和检索结果 | 优先于微调解决知识更新 |

## 推理优化

- **KV Cache**：复用已计算的注意力键值，降低生成后续 token 的重复计算。
- **Batching**：把多个请求合并执行，提高 GPU 利用率，但可能增加排队延迟。
- **量化**：用更低精度表示权重，降低显存和成本，需用 Eval 验证质量损失。
- **Streaming**：改善首 token 后的用户感知延迟，不等于总计算量减少。
- **模型路由**：简单任务用小模型，复杂任务升级，并用回归集约束质量。

## LoRA、QLoRA 与微调决策

微调适合改变稳定行为、格式、术语和风格；不适合替代实时知识库、权限系统或业务规则。

```text
知识经常变化       → RAG
行为/格式长期稳定   → SFT 或 LoRA
需要降低单次成本   → 小模型蒸馏或量化
只是某几个 case 错 → 先改数据、Prompt 和 Eval
```

## 实践任务

1. 用同一组 20 条问题比较大模型、小模型和带 RAG 的效果。
2. 记录输入 token、输出 token、首 token 延迟、总耗时和成本。
3. 为一个结构化输出任务设计 SFT、RAG、Prompt 三种方案，并用同一 Eval 集比较。
